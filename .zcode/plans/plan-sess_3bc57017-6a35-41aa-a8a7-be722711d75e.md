# CodeGuard-Agent 改造实施方案

## Context（背景与目标）

当前 `D:\AI_Comic_Drama-main` 是基于 LangGraph 的漫剧制作多agent系统（12节点状态机）。按照 `PATH_A_CODING_AGENT_PLAN.md`（937行改造计划书）的要求，将其**彻底替换**为 **CodeGuard-Agent：企业级 Repo 自动化 Bug 修复与单测生成 Multi-Agent 系统**，具备完整四能力闭环：

| 四能力 | 承载节点/模块 | 机制 |
|---|---|---|
| ① 自动发现异常 | `machine_review`（AST语法+高危调用+签名契约静态门控）+ `sandbox_execute`（F2P/P2P测试失败与Traceback捕获） | 确定性门控优先，LLM只做补充 |
| ② 规划处理方案 | `director_plan`（AST调用图扫描→Top-K故障文件定位→符号契约冻结）+ `director_resolve`（统筹异常路由自愈策略） | Context Engineering |
| ③ 执行处理 | `write_draft`（Search-Plan-Execute-Reflect四阶段补丁编写）+ `sandbox_execute`（逐槽位ReAct自愈：Act→Observe→Think→Retry） | 复用原 `_react_single_shot` 闭环模式 |
| ④ 检测处理结果 | 沙箱内 **F2P复现测试 + P2P回归测试 + 分支覆盖率** 三重确定性门控，交付零退化 `.patch` | 反幻觉红线 |

用户决策：完整可运行系统（引擎+12节点图+入口）+ **50题确定性评测集** + **彻底替换**漫剧流水线（保留LangGraph骨架与工程底座）。

**彻底替换范围**：包重命名 `src/manga_drama` → `src/codeguard`；删除漫剧域代码（t2i/tts/ffmpeg/consistency/storyboard、漫剧prompts、漫剧nodes、drama_app.py）；保留并复用底座（budget/errors/retry/llm工厂/runtime SSE/SqliteSaver/checkpointer/`_common.py`的`call_llm_json`+`settle_costs`/GraphNodes的partial绑定模式/6计数器+成本熔断）。

## 目标架构

**12节点图（拓扑与现 `graph.py` 同构，仅改节点实现与命名）：**

```
understand(故障解析) → clarify_ask(HITL#1) → director_plan(AST定位+契约冻结)
→ write_draft(四阶段补丁) → machine_review(静态门控)
  ├─ 不通过 → write_draft（machine_revision_count封顶3）
  ├─ 工具级异常 → director_resolve
  └─ 通过 → director_supervise(Tech Lead两阶段自省) → human_review(HITL#2,Diff预览)
→ build_anchors(生成F2P复现测试,沙箱验证Red态) → confirm_anchors(HITL#3)
→ sandbox_execute(逐槽位ReAct沙箱自愈+F2P/P2P/覆盖率门控)
  ├─ 全过 → END（输出fix.patch+覆盖率报告）
  ├─ 未超上限 → sandbox_execute（production_attempt_count封顶2）
  └─ 沙箱环境异常 → director_resolve（retry/downgrade/skip/escalate，封顶3）
```

**新状态 `CodeGuardState`**（替换 `state.py:132` WorkflowState，保留同构字段语义）：
- `brief`→`issue_context`（症状/堆栈/复现条件/完备度）；`character_bible`→`symbol_bible`（`merge_symbol_contracts` reducer，同构于 `merge_character_bible`）；`shots`→`patch_units`（`merge_patch_units`，同构于 `merge_shots`，按unit_id幂等）
- `video_path`→`patch_path`+`coverage_report_path`；新增 `repo_dir`（待修复仓库）、`located_files`、`f2p_tests`/`p2p_tests`（冻结锚点）、`sandbox_result`
- 保留全部计数器原名：`clarification_round/machine_revision_count/human_revision_count/anchor_round/production_attempt_count(→沙箱自愈轮次)/director_resolve_count`
- **关键修复**：新增普通字段 `open_issues`（无reducer、节点返回即覆盖）承担路由信号；`agent_issues` 保留为 append-only 审计日志。彻底解决原系统 `director.py:215` 返回 `[]` 无法清空 append reducer 导致的resolve死循环

**LLM角色表重写**（`llm.py:22` ROLE_MODELS，机制不变）：`understand/understand_summary`(deepseek-chat)、`director_plan`(deepseek-reasoner)、`director_resolve`(deepseek-chat)、`write/write_reflect`(qwen-max/deepseek-chat)、`review/review_verify`(deepseek-chat)、`f2p_writer`(qwen-plus)、`produce_react`(qwen-plus,traceback驱动重写)、3个fallback角色保留。**全部保留 PRICE_PER_1K_CNY 成本采集与 budget 熔断。**

**Task 8 — pipeline_nodes 后段（锚定+执行+统筹）**：`director_supervise`（两阶段自省，反馈保留、决策交人工）、`human_review`/`confirm_anchors`（interrupt，复用 `nodes/human.py` 模式）、`build_anchors`（LLM生成F2P→沙箱Red态验证→冻结）、`sandbox_execute`（**复用 `_react_single_shot` 的Act→Observe→Think→Retry模式**：Act=沙箱写补丁跑pytest；Observe=解析F2P/P2P/覆盖率；Think=produce_react角色分析裁剪后的traceback定向重写该unit；每unit≤2次，production_attempt_count封顶2）、`director_resolve`（异常统筹；**修复①：返回 `open_issues: []` 真正清空路由信号；修复②：max_resolve硬编码检查，超限强制escalate**）、`escalate`（复用 `nodes/escalate.py` 模式）、7个条件路由（均含 `open_issues`/budget/硬封顶检查）。

**Task 10 — 50题评测集 + 消融**：Bug注入器按10类模板×5实例生成50题（每题含微型多文件repo+issue文本+gold_files+F2P/P2P+预烘焙补丁对，约40%题目的first_attempt故意失败于静态门控或F2P使自愈产生真实增益）。`evaluate_agent_on_suite`（真实跑沙箱pytest统计 Localization Recall@3 / One-shot Pass@1 / Multi-turn Resolved Rate / p2p_regression_rate）；`run_ablation_benchmark` 跑3组消融出Markdown+JSON报表。`test_benchmark`：套件构建确定性（两次生成逐字节一致）、healed_resolved_rate > one_shot、p2p回归率=0、Recall@3≥0.9。**遵守反幻觉红线：README中的指标只引用 reports/ 实际产出数字，不写死90%/78%。**

**Task 11 — 彻底替换清扫与终验**：删除 `src/manga_drama/`、`drama_app.py`、漫剧测试、frontend漫剧组件（App.jsx可选最小字段适配）；全量测试；跑一次 `python -m eval.run_benchmark` 落盘报表；手动E2E（见下）。

## 验证方案

1. **单测**：`python -m pytest tests/ -v` 全绿（引擎测试真实跑pytest沙箱，无需API key；节点/图测试用FakeLLM）
2. **评测**：`python -m eval.run_benchmark --suite 50 --out reports/` → 检查 reports/benchmark_report.md 四指标与3组消融对比，healing净增益>0
3. **手动E2E**：用eval导出的demo bug仓库 → `python codeguard_app.py --cli --repo <demo> --issue "<bug描述>"` → 走完3处HITL → 验证产出 `data/codeguard_output/<job>/fix.patch` 可 `git apply`、覆盖率报告落盘、宿主demo仓库未被污染
4. **服务模式**：`python -m codeguard.server` + POST /api/jobs → SSE事件流完整（issue_parsed→plan_ready→static_gate→anchors_ready→unit_progress→patch_done）
