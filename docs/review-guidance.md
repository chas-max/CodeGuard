# 仓库级审查指南 `.codeguard/review.md`

审查 Agent 每次都会读取这个文件。它告诉 reviewer「在这个仓库里，什么才算失败」。

## 信任模型

- **只从 base 分支读取**：PR 里对 `review.md` 的修改不会影响本次审查（会被 `POL-001` 标记）；
- 内容作为数据注入提示词（`<untrusted_data>`），不会被当成指令执行；
- 文件缺失时静默跳过，不阻断流程；
- 全量注入上限 8000 字符，按路径分段，只有命中本次变更路径的分段才会注入。

## 写法

```markdown
# 本仓库审查约定

通用：所有 finding 必须给 `文件:行` 证据；不确定的写低置信度。

## path: src/billing/**
这里的“失败”是金额算错或对账失败，不是命名或排版。
改动必须带一个对账测试；最多 2 条 nit。

## path: docs/**
文档的失败是“它撒谎了”（描述与代码不一致），不是排版问题。

## path: migrations/**
迁移必须可回滚；没有 downgrade 路径就直接 blocking。
```

### 分段规则

- `## path: <glob>` 开始一个分段，glob 支持 `docs/**`、`**/auth/**`、`**/*.md`；
- 第一个 `## path:` 之前的内容是**前言**，对所有路径生效；
- 一个变更路径命中多个分段时，所有命中的分段都会注入。

### 建议写进去的内容

| 内容 | 例子 |
|---|---|
| 这里的失败长什么样 | 「配置错误 = 请求被静默路由到错误后端」 |
| 必须给的证据 | 「必须给文件:行，不接受凭函数名猜测」 |
| nit 上限 | 「最多 2 条非阻塞建议」 |
| 跳过哪些路径 | 「`generated/`、`vendor/` 不要报」 |
| 该仓库特有的红线 | 「金额、幂等键、审计日志字段不得变更语义」 |

## 与 policy 的分工

- `policy.yml` 决定**流程**：谁能合、几级风险、几票审批、跑什么检查；
- `review.md` 决定**判断标准**：什么算问题、证据要求、噪音上限。

两者都放在 `.codeguard/` 下，都只读 base。策略 schema 非法会 fail-closed；`review.md` 缺失或格式不对只会被忽略。
